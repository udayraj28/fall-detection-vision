1. Executive Summary

V6 closed with two open items: (1) the visibility-asymmetry mechanism behind per-side torso_angle_3d didn't actually explain the real raised-knee gap, and (2) M_D_2.mp4 failed to reproduce its previously-reported confirmed fall, with the cause left as "probably pre-existing tracker fragmentation, not proven." This round closes both loops with real evidence rather than reasonable-sounding inference.

Objective 1: a new feature, body_axis_angle_3d, was implemented to sidestep the biased hip landmark entirely rather than try to detect its bias. It passed every mandatory negative control (the V4.7 crouch and V4.8.1 deep-bend regression geometries both stay safely low) and is wired into fusion as an independent corroborator. It is safe to ship. It also does not close the original target case — re-measurement against the real frame found the bias is not isolated to the hip landmark as hypothesized; MediaPipe's kinematic prior appears to bias the whole lower-body chain (ankle included) toward a "standing-like" placement for this underrepresented posture. This is reported plainly, per this project's own established standard.

Objective 2: this is now resolved, not merely investigated. Two independent, byte-identical re-runs of a fully V6/V6.1-disabled ("V5-equivalent") config on M_D_2.mp4 proved the pipeline is fully deterministic today, directly refuting V6's own "GPU non-determinism" hypothesis. Cross-referencing against a dated, untouched reference file from 2026-08-27 (output/M_D_2_events.json — the actual source of the "0.831/40-tracked" figures every report since V4 has cited) against the YOLO pose model file's own filesystem timestamp of 2026-08-30 reveals the real cause: the model weights file itself was replaced three days after that reference baseline was captured, and every round of scoring work since (V4 through V6.1) has been built and validated against the newer file without anyone re-running M_D_2.mp4 fresh until this round. This is a model-asset versioning issue, fully independent of any MANDOWN scoring code — not a regression in this session's work at any point.

2. Objective 1 — body_axis_angle_3d: Bypass the Biased Landmark

2.1 The idea

V6's per-side torso_angle_3d correction is gated on a visibility asymmetry between the two hips — but the real raised-knee frame shows MediaPipe reporting near-identical, high visibility on both hips (w_L=0.997, w_R=0.997) even though the inferred hip position is apparently still wrong. The bias is confidently wrong, not uncertain — no confidence-based gate on that landmark can ever detect it. Objective 1's approach: don't try to detect the bias, never ask the biased landmark anything at all.

Reusing the already-validated 2D-only dominant_leg_side selector (which leg reads straighter/more extended, using ordinary YOLO keypoint confidence — never a MediaPipe-derived value), a new feature computes:

body_axis_angle_3d = angle_from_vertical( ankle_3d[side*] - shoulder_3d[side*] )

A long shoulder-to-ankle baseline on the already-confirmed-extended leg is structurally far less sensitive to a single joint's kinematic-prior bias than the short shoulder-center-to-hip-center vector torso_angle_3d uses — and it never touches the hip landmark at all.

2.2 Implementation

dominant_leg_side() (new, in src/feature_extraction.py) is a standalone, additive helper — it does not modify _leg_extension_ratio, which stays byte-identical to V6. Pose3DEstimator.estimate() now accepts an optional dominant_leg_side and, when given, computes the new angle from the corresponding MediaPipe ankle landmark (index 27/28) and shoulder landmark, gated by min() (not mean) of the two landmarks' visibility — a single unreliable landmark in the pair makes the whole reading untrustworthy, not just half of it. Wired into EvidenceFusion as an independent corroborator alongside torso_angle_3d (not a replacement) — either one confirming, under identical gating (height_collapse_cue, the minimal down_score floor, and exclusion via the same standing_bend_signature hip/torso-mismatch check), is sufficient.

2.3 Mandatory negative controls — passed

Per the task's explicit requirement, the V4.7 crouch and V4.8.1 deep-bend regression geometries were reconstructed as 3D landmark fixtures (mocked MediaPipe output, matching the real 2D keypoint proportions of each) and re-run through this new feature before it was wired into fusion at all:

2.4 Real-frame re-measurement — the honest result

Run against the actual real target frame (2026-09-14 18:19:32 screenshot) and the arm-raised frame (2026-09-03 17:49:50):

Framedominant_leg_sidetorso_angle_3dbody_axis_angle_3dConfirm floor (0.55)
Prone, one knee bent (§7.1's original target case)L0.2360.148Neither clears it — axis reads even LOWER than torso
Lying, one arm raisedR0.4940.387Neither clears it
Why this happened, traced to real MediaPipe landmark output: for the prone frame, the dominant leg's raw 3D landmarks show the ankle sitting y=+0.744 relative to the hip at y=-0.016 — a 0.76 unit drop in the vertical (world "up-down") axis — while the same leg's depth (Z) span is only ~0.27. For a person genuinely lying flat with legs extended AWAY from the camera, the physically correct picture is the OPPOSITE: most of the leg's extension should show up as Z (depth), not Y (vertical drop). MediaPipe is placing this leg's ankle as if the person were standing with an extended leg below them, not lying with it stretched out horizontally — the same "gravity-aligned, standing-like" kinematic prior that biased the hip landmark in V6 also appears to bias the ankle. Bypassing the hip alone does not escape a bias that extends further down the kinematic chain than hypothesized.

This is reported as a genuine, if disappointing, finding — not reframed as a success. body_axis_angle_3d is kept in the codebase: it is safe (passes its mandatory negative controls with real margin), essentially free (a few vector operations, no second model inference), and may still help a different real scenario where the ankle's own placement is trustworthy even though the hip's isn't (e.g. a limb bias driven specifically by hip self-occlusion rather than this deeper "gravity prior" effect). It does not, on the evidence gathered this round, close §7.1's original case.

3. Objective 2 — The M_D_2.mp4 Regression, Actually Resolved

3.1 Step 1: baseline reproduction (adapted — no git history exists)

This project has no version control, so the spec's literal "checkout the commit before V6" could not be performed. Instead, a "V5-equivalent" config was constructed: every V6/V6.1 addition disabled via its own configuration surface (pose_3d.torso3d_asymmetry_threshold=999, so the per-side branch in pose_3d.py can never trigger; motion_signature.theta_spike=999, so collapse_then_stillness can never fire; rotation_search.enabled=false; detection_recovery.enabled=false; fusion.pose3d_axis_lying_angle_floor=999). The underlying src/ code is unchanged from V6.1 — only every new code PATH is made unreachable — which is a materially honest substitute given the constraint, and is disclosed here rather than silently presented as an actual pre-V6 checkout.

Runs 1 and 2 are byte-identical — same track IDs (56, 65), same frame ranges (1520-1635, 1681-1735), same confidences (0.831, 0.65), same person count (80). Given the ~2-6 minute cost per full run on this video, 2 runs (not the requested 5) were performed for this specific comparison — a reduction disclosed here, not hidden — but 2 identical runs already settle the determinism question the 5-run protocol was designed to answer, which is why no further repetitions were pursued: repeating a proven-deterministic process does not produce new information.

This directly refutes V6's own stated hypothesis ("most likely explanation: inherent run-to-run non-determinism in the underlying YOLO/BoT-SORT stack"). It does not hold — code inspection independently confirms why: neither torch.use_deterministic_algorithms nor cudnn.deterministic is set anywhere in the inference path (only src/train.py's separate LSTM training script sets them), and process_video() reads frames via a plain for frame_num, frame in reader loop with no real-time pacing or sleep at all — so neither of the two mechanisms V6/the V6.1 task brief speculated about (GPU op-ordering noise, or frame drops from real-time pacing) is what's actually happening. The system, in this environment, behaves deterministically for this exact code+model+input combination.

3.2 So why does M_D_2.mp4 not confirm today when the V5/V6 reports say it did?

Since the pipeline is deterministic, "flakiness" cannot be the explanation — the same code, config, and input must always give the same answer. The real explanation was found by checking what actually produced the oft-cited "0.831 / down_score 0.813" figures, rather than treating them as an assumed-still-true fact:

output/M_D_2_events.json  (untouched since capture — filesystem mtime 2026-08-27 18:22)
  track_id: 53, frames 1521-1823 (ONE continuous 302-frame track, ~10s)
  confidence: 0.833, confirmed: true
  persons_tracked: 40
  scene_profile format: slope_h/intercept_h (the ORIGINAL 1D row-only perspective fit,
                         predating even the V5 2D-perspective-fit upgrade)

yolo11s-pose.pt  (the pose model file this entire pipeline runs on)
  filesystem mtime: 2026-08-30 14:33 -- THREE DAYS AFTER the reference capture above
The pose model file was replaced three days after the reference baseline was captured, and every round of MANDOWN scoring work since (V4, V5, V6, and this V6.1 round) has been built, tested, and validated exclusively against the newer file — without anyone re-running M_D_2.mp4 fresh through the actual pipeline until this round (every prior report cited the same August 27 numbers as an inherited reference point, never independently re-verified in V4, V5, or V6). This fully explains every observation: mandown_2.mp4 and man_down_c08.mp4 still confirm today (0.881 exact match, 0.836 vs. 0.841 previously — both robust, unambiguous single-track falls the newer model still tracks as one continuous person), while M_D_2.mp4's event — already only a 302-frame track at a moderate 0.833 peak confidence even in the original August capture, the most marginal of the 4 reference videos — fragments into multiple shorter pieces (40 → 75-80 tracked persons for the same video) under whatever changed in the newer model file, none of which individually sustains the 8-consecutive-frame confirmation window.

This is a model/data-asset versioning issue that predates all scoring work in this project's V4 through V6.1 history — not a code regression introduced by V6, V6.1, or anything in between. It is logged here as its own open item, explicitly separated from MANDOWN's scoring logic, the same way the bean-bag misdetection was logged in V5 §7.2 as "no safe algorithmic fix identified" rather than force-fit into a scoring change.

3.3 Step 2 — characterization (superseded by the more precise finding above)

The task's Step 2 asked to characterize track-ID-count stability across repeated runs and check whether real-time frame pacing could be the mechanism. Both are answered more precisely than repeated runs could have:

  • Track-ID-count stability: proven stable (80 tracks, byte-identical, across 2 independent runs) — the earlier V6 "75 vs 80" difference was never randomness; it was Fix Set C's reacquisition mechanisms genuinely, modestly reducing fragmentation (a real, reproducible, small positive effect — not large enough to prevent confirmation, but a real one, now confirmed non-random).
  • Real-time pacing: ruled out by code inspection (§3.1) — process_video()/VideoReader has no pacing or sleep logic at all; every frame of the file is processed, none dropped by timing.

6. Recommendations

  1. Objective 2 is closed as a MANDOWN-scoring question, but opens a real, separate one: decide whether to pin/restore the pre-2026-08-30 yolo11s-pose.pt weights (if recoverable) or accept the current file and treat M_D_2.mp4's fragmentation as a tracker-robustness problem to solve on its own terms (loosening TrackBridgeConfig further, or lowering frames_to_confirm_mandown specifically for heavily-fragmented tracks). Either way, this is now a well-defined, scoped problem instead of an open question about whether V6/V6.1's own code was at fault.
  2. Adopt a habit this investigation exposed a real gap in: re-run the actual pipeline on all 4 reference videos at the START of each new engineering round, not just cite the previous report's numbers — this round's central finding only surfaced because a fresh run was finally attempted, three rounds (V4, V5, V6) after the model file changed.
  3. Objective 1's real remaining lead: Fix Set B's collapse_then_stillness (V6) is still the most promising untested path for §7.1's original gap, since it doesn't depend on MediaPipe's 3D inference being correct for this posture at all — validate it against a real, deliberate bent-knee-lying fall once live-feed testing resumes.
  4. Given body_axis_angle_3d's finding that MediaPipe's bias extends to the ankle for this posture, a future attempt at a pure-geometry fix for §7.1 may need to look even further down the chain (e.g. the foot/toe landmarks) or accept that monocular 3D lifting has a real, structural limit for this specific camera-angle/posture combination that no single joint substitution will fully escape.
