1. Executive Summary

This round targeted two problems left open by the V5 report: (1A) a foreshortened-lying person whose limbs are posed asymmetrically (a raised knee, a raised arm, an arm tucked under the torso) still doesn't reliably confirm, because every existing angle feature averages left/right keypoints into one midpoint — an implicit symmetry assumption that breaks exactly for this posture; and (1B) the pose model itself sometimes produces no detection at all for a person already on the floor, undercounting a visibly-present fallen person.

Three fix sets were implemented, all gated to be either provably monotonic with respect to every existing confirmed case, or purely additive/fallback-only, so the single most protected real regression case in this project (M_D_2.mp4) could not be made worse by construction. This report documents exactly what was built, what real measurement showed, and — matching this project's established discipline of recording negative results, not just successes — an important honest finding: the specific visibility-asymmetry mechanism Fix Set A targets does not actually explain the real §7.1 gap once re-measured against the real MediaPipe output for that exact frame. The fix is safe and kept (it cannot regress anything and may help other real cases), but it did not close the original target case on its own. Fix Set B (a temporal, not geometric, confirmation path) is the more promising path for that specific gap, but by its own nature can only be validated on real video with genuine motion — untestable on the static images available this round.

A serious-looking regression was also investigated this round: a fresh run of M_D_2.mp4 today produced 0 confirmed falls instead of the previously-reported 1. After a careful investigation (§7), this was traced to this video's own already-documented tracker-fragmentation behavior (75-80 track IDs for one physically continuous person), not to anything in this round's code changes — but it means the literal "exact-match" re-verification requested could not be produced this round, and this is reported transparently rather than papered over.

2. Problem Restated: Two Independent Failure Modes

2.1 (1A) Asymmetric foreshortened-lying postures

Every angle feature in the pre-V6 pipeline (torso_angle, hip_angle, the 3D-lifted torso_angle_3d) is computed from the midpoint of the left/right shoulder or hip pair, or the midpoint-derived 3D center MediaPipe infers. Averaging two limbs into one number is an implicit symmetry assumption. Foreshortened lying is exactly the case where that assumption breaks: one limb reads unambiguously "lying," the other reads "bent/raised," and the average sits in the ambiguous middle where nothing confirms — documented in the V5 report as the open §7.1 case (a person lying on their back with one knee raised): torso_angle_3d=0.319 (below the 0.55 floor), down_score=0.454 (below the 0.65 floor), floor_proximity=0.552 (below the 0.70 floor).

2.2 (1B) The pose model itself sometimes fails to produce a detection at all

YOLO-pose, like nearly every pose model, is trained overwhelmingly on upright/walking/sports imagery. Prone, floor-level, foreshortened bodies are underrepresented in that distribution, so both detection confidence and keypoint quality degrade on exactly the frames MANDOWN most needs to see clearly — a data-distribution problem in the frozen model, worked around at inference time (not fixed by retuning fusion thresholds, and not by retraining).

3. Fix Set A — Per-Side (Asymmetric-Aware) Geometric Features

3.1 §2.1 — Per-leg leg_extension_ratio

Investigation found this selection rule was already implemented, independently, in an earlier engineering round: ExtendedFeatureExtractor._leg_extension_ratio computes each leg's hip→knee→ankle extension ratio separately and only includes a leg whose three keypoints are all confidently visible; when exactly one leg qualifies, that leg's ratio is used alone (never blended with a low-confidence value); when neither qualifies, it returns a neutral "no bend evidence" default rather than fabricating one. This is functionally identical to the V6 spec's requested selection rule. New tests (TestLegExtensionRatioPerSideSelection, in tests/test_extended_features.py) now assert this exact behavior explicitly, closing the gap between "this happens to already work" and "this is verified to work."

No threshold value was changed here: the spec's suggested τ_vis=0.5 (vs. the existing 0.3) was deliberately not adopted, since the spec's own guidance explicitly warns against tuning this in isolation from a large real keypoint-confidence dataset, which this round did not have (no live feed).

3.2 §2.2 — Per-side torso_angle_3d, provably monotonic via max()

Implemented in src/pose_3d.py. When one side's shoulder+hip MediaPipe landmarks are confidently more visible than the other's by more than Pose3DConfig.torso3d_asymmetry_threshold (0.3, a design margin — the spec's own suggested starting point), that side's own shoulder→hip vector is computed as a second candidate angle, and the larger of it vs. the existing bilateral (midpoint) reading is kept:

torso_angle_3d = max(bilateral_angle, single_side_angle)   # only when |w_L - w_R| > threshold
                                                             # else: bilateral_angle, byte-identical to pre-V6
Why this is provably monotonic: a symmetric-visibility body (the common case, including every existing confirmed real fall in this repo) takes the unchanged bilateral-only path — zero behavior change. An asymmetric-visibility body can only have its angle raised relative to the pre-V6 value, never lowered, since max() never selects a smaller number over the one that was already there. This means the fix cannot regress any existing confirmed case by mathematical construction, independent of any live-camera re-verification.

Verified with 5 new unit tests (TestPose3DPerSideMonotonicMax, tests/test_pose_3d.py) using a mocked MediaPipe result for precise control: symmetric visibility stays byte-identical to bilateral; an asymmetric fixture modeled on the real §7.1 corruption mechanism (a raised knee pulling one hip toward the shoulder) shows the single-side reading correctly wins via max(); a visibility gap below the threshold stays bilateral (no over-triggering on ordinary noise); a genuinely upright person with incidental visibility asymmetry stays correctly low (both readings are low, so max() changes nothing).

3.2.1 Real-image re-measurement — the honest finding

Re-running this exact fix against the real §7.1 frame (2026-09-14 18:19:32 screenshot) to see whether it actually raises torso_angle_3d for the real target case produced a genuinely important, unglamorous result:

L_SHOULDER visibility=0.999   L_HIP visibility=0.998
R_SHOULDER visibility=0.999   R_HIP visibility=0.997
w_L = 0.997   w_R = 0.997   |w_L - w_R| = 0.0002   (threshold: 0.3 -- NOT crossed)
=> per-side path never activates; result stays bilateral-only: torso_angle_3d = 0.236
MediaPipe is confidently wrong here, not uncertain. The hypothesis behind Fix 2.2 was that a raised knee drags visibility DOWN on the corrupted side, creating a detectable asymmetry. On this real frame (and on 2 other real lying postures re-measured the same way — the "arm raised" and "symmetric lying" screenshots, see §6), MediaPipe reports near-identical, high visibility on both sides even though its inferred 3D position is apparently still off for this posture. The corruption here is a genuine 3D-pose-inference inaccuracy for an underrepresented posture, not a visibility-detectable asymmetry — so the specific mechanism this fix targets does not explain, and does not close, the original real gap it was written for.

The fix is kept anyway: it is safe (provably monotonic, independently unit-tested), free (near-zero extra cost — the extra angle computation is a few vector operations, not a second model inference), and may still help a different real scenario where visibility genuinely does diverge (e.g., a limb entirely outside the frame or heavily occluded by furniture, rather than merely differently posed). It is reported as "implemented and safe, did not close the target case" rather than overclaimed — the same honesty standard the V4.7/V4.9 investigations in the V5 report were held to.

3.3 §2.1's hip_angle per-side replacement — deliberately NOT implemented this round

The spec also requested a per-side, asymmetric-aware hip_angle. This was evaluated and not implemented, for a specific, provable safety reason rather than a time constraint: hip_angle currently feeds a subtractive exclusion gate — the V4.9 hip_torso_mismatch signal (mismatch = torso_angle - hip_angle) that protects against the real deep-bend false positive documented in the V5 report. Raising hip_angle for an asymmetric case would shrink that mismatch, making the bend-exclusion signature less likely to fire — i.e., a change that helps one real case could simultaneously weaken the protection for a different, already-fixed real false positive. Unlike torso_angle_3d (where "higher is always more like lying, so raising it is always the safe direction"), hip_angle sits on both sides of this tension at once, so no single max()/min() trick makes it safe in both directions simultaneously without a live-footage re-verification pass this round did not have access to. Deferred, and flagged as the top open item in §9 — this mirrors the V5 report's own precedent of reverting/deferring a change the moment its safety could not be proven, rather than shipping something merely "probably fine."

4. Fix Set B — Motion-Signature Confirmation Path

A purely temporal, not geometric, confirmation path: collapse_then_stillness, computed per track in MandownTrackContext and consumed as a new, additive rule 8 in EvidenceFusion. A hard 0/1 gate (never blended), True only when all of:

  1. a genuine body_height_norm collapse of at least theta_spike within a 1-second window, somewhere in the last t_lookback_seconds + t_still_seconds;
  2. continuous stillness (per-frame keypoint motion energy below theta_still) held from that spike through to now, for at least t_still_seconds;
  3. a real, currently-elevated height_collapse_cue (reuses the same calibrated floor established in V4.2-V4.9);
  4. the track is not currently inside its own confidently-standing baseline.
if collapse_then_stillness and pose_quality >= pose_quality_floor:
    fusion_score = max(fusion_score, confirmed_mandown_threshold)   # same style as V4.10's direct down_score path

This is additive by construction — it can only ever raise the fusion score for a track already backed by a real, sustained height collapse; it cannot fire for, and cannot suppress, anything else.

Per the spec's own instruction, theta_spike/theta_still were measured from this repo's 2 real single-fall videos via a dedicated diagnostic pass (not a live camera — these are pre-existing repo assets):

Per the spec's own explicit acknowledgment, the TRUE-POSITIVE path is inherently temporal and cannot be exercised on a static image. What was run: feeding one of the real still images repeatedly as a synthetic zero-motion, zero-height-change 200-frame "sequence" —

5. Fix Set C — Detection-Recovery for Missed Poses

5.1 §4.1 — Narrow-range rotation search

Implemented in src/detector.py as PersonDetector.redetect_in_roi_with_rotation, run only when the existing plain straight-crop re-acquisition (redetect_in_roi, unchanged) has already failed to find a previously-tracked person at all — i.e., strictly rarer than the spec's own proposal (which would try rotation alongside the plain retry on every trigger). Tries {prev_best-15°, prev_best, prev_best+15°} on the same padded ROI using the same frozen model (no retraining), keeps whichever candidate gives the highest mean keypoint confidence, and decays the remembered best angle back toward 0 (×0.9/frame) when not re-triggered.

Mechanism-level validation (real image)

Both real §7.1-adjacent fixtures were already confidently, correctly detected in their original frames (det. confidence 0.827 and 0.909) — i.e., Problem 1B does not manifest in these exact two frames, so no "before/after recovery" could be demonstrated on them specifically (an honest limitation, reported rather than manufactured). A direct mechanism check was run instead: the real standing person from the arm-raised screenshot was synthetically rotated by known amounts and re-detected:

Synthetic tiltPlain straight-crop mean keypoint conf.Rotation-search mean keypoint conf.
15° (within the ±15° search window)0.7740.811 (won at +15°)
45° (exceeds the narrow search window)0.826*0.826 (won at 0° — correctly could not reach 45°)

*YOLO-pose was itself fairly robust to the 45° case here on this particular crop (padding_ratio=0.6 retains enough context) — a real, modest improvement was measured within the search window, and the boundary case correctly shows the narrow-search design limiting itself rather than silently failing.

5.2 §4.2 — Confidence-decayed keypoint carry-forward

Implemented as MandownTrackContext.extrapolated_keypoints: constant-velocity extrapolation from the track's last 2 confident raw keypoint arrays, with confidence decaying by confidence_decay_factor (0.85) per frame since the last real detection, capped at t_gap_max_seconds (3.0s) of continuous non-detection before the track is dropped for real. Wired as a last-resort fallback in _reacquire_lost_tracks — only when both the plain retry and the rotation search have failed — and fed into frame_result.persons exactly like a real detection, so the existing pose_quality_score discount handles decaying trust with zero new fusion-side code, per the spec's own composability goal.

As the spec itself anticipates, this path is untestable on a single static image (it requires an actual multi-frame detection gap). It is unit-tested at the mechanism level (constant-velocity extrapolation math, confidence decay, insufficient-history graceful failure — TestExtrapolatedKeypoints), but its real-world behavior on an actual brief occlusion is deferred to live-feed testing, exactly as instructed.

7.2 M_D_2.mp4 — the protected track: NOT reproduced this round

Two fresh, full runs of M_D_2.mp4 today (with, and separately without, Fix Set C entirely disabled) both produced 0 confirmed MANDOWN events, versus the 1 confirmed event (confidence 0.831, down_score 0.813) documented in the V5 report. This is reported transparently, not minimized.

Investigation

  • Track fragmentation, not scoring failure: both runs show 75-80 total tracked persons for this one video (vs. 1-8 for the other 3 reference videos) — consistent with this project's own pre-existing, already-documented observation (TrackBridgeConfig's own code comment: "one real validation video went from a handful of tracks to 74 under current settings" — almost certainly this same video). At least 3 separate track fragments in today's run individually reached genuinely strong MANDOWN-tier evidence at their peak frame (down_score 0.643-0.808, fusion_score 0.79-0.828, suggested_tier: "MANDOWN"), but none individually sustained the 8 consecutive confirming frames StateMachineConfig requires before the fragmentation split them apart again.
  • Fix Set C ruled out: disabling rotation search and confidence-decayed carry-forward entirely did not restore confirmation — if anything, the disabled run showed more fragmentation (80 tracks) than the enabled one (75 tracks), the opposite of what a Fix-Set-C-caused regression would predict.
  • Fix Set A/B ruled out mathematically: §3.2's per-side torso_angle_3d uses max() and §4's collapse_then_stillness is a pure OR-additive rule — both are provably incapable of lowering any score for any input, so neither can be the mechanism behind a track that used to confirm no longer doing so.
  • Most likely explanation: inherent run-to-run non-determinism in the underlying YOLO/BoT-SORT stack (unpinned CUDA op ordering is a well-known source of small run-to-run differences in deep learning inference), compounding over a long, heavily-fragmented video (3718 frames) into a different track-ID split than whichever run produced the V5 report's figures.

Conclusion, stated plainly: the literal "exact-match re-verification with zero regression" this report was asked to produce could not be achieved this round for this specific video, and no amount of re-running alone would prove it either way, since the system's fragmentation behavior for this video is not observed to be stable run-to-run even before considering any V6 change. The mathematical monotonicity of every V6 scoring change, combined with the clean exact/near-exact matches on the other 3 reference videos (which do not suffer this fragmentation), is the strongest evidence available this round that V6 itself did not cause this — but it is evidence, not proof, and is reported as an open item rather than a closed one. See §9 for the recommended next step.

10. Recommendations

  1. Highest priority, blocking full confidence in this round: re-run M_D_2.mp4 a few more times (with no code changes at all) to determine whether 0-confirmed is itself the more common outcome for this video under current tracker settings, independent of V6 — this would mean the V5 report's own 1-confirmed result was the fortunate run, not the reliable one, and the real fix needed is tracker-fragmentation robustness (loosening TrackBridgeConfig's IoU/recency further, or investigating why BoT-SORT loses this specific track so often), not anything in this report.
  2. Live-feed re-test of Fix Set B against a real, deliberate fall in the bent-knee-lying posture — the only way to validate the true-positive path of collapse_then_stillness, and the most promising remaining avenue for closing §7.1's original gap given §3.2.1's finding that the visibility-asymmetry mechanism doesn't explain it.
  3. Live-feed re-test of Fix Set C §4.2 (confidence-decayed carry-forward) against an actual brief occlusion — untestable on any static image by construction.
  4. Revisit per-side hip_angle (§3.3) once live footage is available to directly re-verify it doesn't reopen the V4.9 deep-bend false positive, the same discipline already applied to torso_angle_3d.
  5. Continue this project's established validation discipline for any future change: real-measured thresholds over guessed ones, explicit negative-control tests, and a full M_D_2.mp4 re-run before considering any scoring change complete — understanding now that this specific video's tracker fragmentation may need several repeated runs, not one, to draw a reliable conclusion.
